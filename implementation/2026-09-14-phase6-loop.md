# Phase 6 — The Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Harvest → splice → fight → reward closes without leaving the app — and a deployment the player does not own becomes inexpressible rather than merely refused, which is the sentence `specs/plans/broodline_phase5_validation.md` §2.2 forbade Phase 5 from claiming.

**Architecture:** The phase opens in the engine, because every layer above it depends on the trait enum's width. `Trait` goes from two values to five and `RaiderType` from one to three, which is a **behaviour change to the engine** and therefore bumps `SimVersion` — Task 1 pays that cost and re-proves the corpus and the device round-trip rather than assuming content addition is inert. Above that: one migration carrying six tables, two pure functions (`nodesFor`, `accrue`) that take a timestamp rather than reading a clock, a splice whose forecast and roll are **one distribution with two callers**, and the deployment moving to `wave/start` where it can be checked against a roster before a simulation is paid for. The phase closes on Phase 5's marker test flipping from asserting a hole to expecting `409`.

**Tech Stack:** Unchanged from Phase 5. .NET 10 / ASP.NET for `sim`, `netstandard2.1` engine. Node 22 LTS, pnpm workspaces, Hono, Drizzle + drizzle-kit, `pg`, Zod + `@asteasolutions/zod-to-openapi`, Vitest, Testcontainers, Postgres 16. Unity 6000.6.0f1 / IL2CPP for `Broodline.UI`. No new infrastructure — no scheduler, no deployable, no bucket.

## Global Constraints

**The engine constraints from Phases 1–3 bind `engine/`** — no floating point, no `System.Math`, no `System.Linq`, no `Dictionary`, no `HashSet`, no `System.IO`, zero project references, the Cecil float scan, `BannedSymbols.txt`.

**Unlike Phase 5, this phase DOES modify `engine/`.** Task 1 is the only task that may. Every constraint above still applies to what it writes: the new trait effects and raider mechanics are integer arithmetic over dense arrays iterated in id order, with every comparator producing a total order tie-broken on spawn index. If a later task appears to need an engine change, stop — the phase is scoped so that it does not, and a second engine change re-opens the corpus baseline Task 1 just re-established.

From `specs/plans/broodline_phase6_loop.md`, and normative here:

- **`api` never parses a replay.** It forwards bytes to `sim` and reads back a verdict (design §6.2, `solo_execution` §6.1). The deployment reaches `api` as **creature ids on `wave/start`**, never by reading the replay.
- **There is no path from a client-supplied value to a `CreatureSpec`.** Specs are resolved from owned rows only (design §2.1, §6.1). This is the mechanism; a handler that builds a spec from request fields has reintroduced the hole.
- **The splice's forecast and its roll are one function.** `preview` returns the distribution, `commit` samples it (design §5.1). Two functions make the published odds a claim about code instead of a property of it.
- **The splice roll is server-side, including the mutation roll** — `data_model` §8, in the strongest terms that document uses.
- **Accrual and rotation take a timestamp; they never read a clock** (design §4.1, §4.2). This is what makes a weekly tick a unit test.
- **Accrual is integer arithmetic with the rate as a rational.** It feeds a ledger credit; a float that drifts a thousandth per claim is an unfalsifiable currency bug (design §4.2).
- **Clamp to the twelve-hour cap first, then bound by remaining yield** (design §4.2). The other order reports units the node cannot supply.
- **Lineage retention is in the first migration that creates `creatures`** (design §3.2, `solo_execution` §5.6). Retrofitting means reprocessing every row.
- **Creature ids are never reused, including for tombstones** (design §3.2).
- **Every currency mutation writes a ledger row in the same transaction as the balance update.** Phase 4's rule, unchanged.
- **`server_id` still leads every primary key and index on every server-scoped table.** RLS on, `FORCE ROW LEVEL SECURITY`, transaction-scoped `set_config`.
- **Generated clients are committed and never hand-edited**, in both directions, and one script regenerates both.
- **A schema migration and the code requiring it never deploy together.** Expand, deploy, migrate, contract.

/// Wave 7, from broodline_waves_01_12.md: "1 Lash · 6 Skirmishers .
/// Integrity 3 . Lash t=4, Skirmishers from t=6, 1.5s apart".
/// The recovery wave after wave 6's designed loss.
public static WaveDef Wave7()
{
    var spawns = new SpawnEntry[7];
    spawns[0] = new SpawnEntry { Tick = 4 * Stats.TicksPerSecond, Type = RaiderType.Lash };
    for (int i = 0; i < 6; i++)
        spawns[i + 1] = new SpawnEntry
        {
            Tick = 6 * Stats.TicksPerSecond + i * 45,   // 1.5s = 45 ticks
            Type = RaiderType.Skirmisher
        };

    return new WaveDef(id: 7, integrity: 3, laneCount: 1, spawns: spawns);
}

public static WaveDef ForId(int id)
{
    if (id == 6) return Wave6();
    if (id == 7) return Wave7();
    throw new WaveCompositionException("no authored wave with id " + id);
}

- [ ] **Step 6b: Splash's mechanic — added during execution**

> **This step was missing from the plan and is the reason it exists.** The Values
> table gave Splash's three tiers but no implementation step and no test, so Task 1
> shipped it declared-but-inert: `Counters.cs` lists it among the deferred, and
> `Diagnosis.CapacityFor` returns `0` for it. **Wave 7 is 1 Lash + 6 Skirmishers and
> Skirmisher's counter IS Splash**, so the wave this phase authored had no working
> answer for six of its seven spawns. Ruled: implement it.

`combat_numbers` §4.2, verbatim: Splash hits **2** targets within 1 tile at tier I,
**3** at tier II, **5** at radius 2 at tier III.

```csharp
// Stats.cs - the simultaneity ladder, matching Chill's and Taunt's shape.
public static int SplashTargets(int tier) => tier switch
{
    1 => 2, 2 => 3, 3 => 5, _ => 0
};

public static int SplashRadius(int tier) => tier == 3 ? 2 : 1;
```

Then wire it the way the two working counters are wired, and no other way:

- `Capacity.TotalSplashCapacity(s)` beside `TotalChillCapacity` / `TotalTauntCapacity`.
- `Diagnosis.CapacityFor` gains `if (trait == Trait.Splash) return Capacity.TotalSplashCapacity(s);` — without it a Skirmisher breach reports **coverage** as its diagnosis, which is the wrong explanation shown to the player.
- Remove `Splash` from `Counters.cs`'s deferred list.

**Target selection is where the determinism risk lives.** Splash hits *N* targets
within a radius, so it needs an ordering over candidates, and `solo_execution` §12
requires every comparator to produce a **total order tie-broken on spawn index**.
Two raiders at equal distance without that tie-break diverge between CoreCLR and
IL2CPP — the one class of bug the cross-runtime gate exists to catch, and the one
that will not show on your machine.

Test it the way Step 6 tests Taunt — on **who is hit**, never on damage, since
`combat_numbers` §4.2 is explicit that no counter has a damage component:

const MAX_OFFLINE_MS = 12 * 3_600_000

/**
 * Integer throughout. The rate arrives per HOUR and is applied over
 * milliseconds, so the division is done once at the end against a
 * denominator that is exact - never as a per-tick float that accumulates.
 *
 * Multiplier tiers come from base_stock §3.1 as hundredths, so arrayTier
 * 1 is 100 and the /100 is exact rather than a rounding site.
 */
export function accrue(a: AccrueArgs): number {
  const elapsedMs = Math.min(a.now.getTime() - a.lastSettledAt.getTime(), MAX_OFFLINE_MS)
  if (elapsedMs <= 0) return 0                       // clock skew pays nothing

  const mult = shardMultiplierHundredths(a.arrayTier) // tier 1 -> 100

  // TELESCOPING, not per-interval. The obvious form -
  //   floor(elapsedMs * rate * mult / (3_600_000 * 100))
  // - is WRONG and this plan shipped it wrong. At 20/hour one minute is
  // floor(0.333) = 0, so 720 one-minute claims accrue NOTHING while a single
  // 12-hour claim accrues 240. Every partial unit is floored away on each
  // call, and a player who checks in often is paid strictly less than one who
  // does not. Taking the difference of two ABSOLUTE floors carries the
  // remainder across calls instead, so the sum over any partition of an
  // interval equals the whole. BigInt because the numerator exceeds 2^53 for
  // long spans. (Found in execution by the drift test below.)
  const start = BigInt(a.now.getTime() - elapsedMs)
  const end   = BigInt(a.now.getTime())
  const num   = BigInt(a.ratePerHour) * BigInt(mult)
  const den   = 3_600_000n * 100n
  const units = Number((end * num) / den - (start * num) / den)

  // Bound AFTER the cap, never before - design §4.2.
  return a.remaining === null ? units : Math.min(units, a.remaining)
}

/**
 * One transaction. The Hatchery check happens BEFORE it opens, so a full
 * roster costs nothing and credits nothing - design §4.3.
 */
export async function claimNode(tx: Tx, serverId: number, playerId: string,
                                slot: number, now: Date): Promise<ClaimResult> {
  const ark   = await loadArk(tx, serverId, playerId)
  const epoch = epochFor(await loadServer(tx, serverId), now)
  const node  = nodesFor(serverId, ark.regionId, epoch, serverSeed, bundle)
                  .find(n => n.slot === slot)
  if (!node) return { kind: 'unknown_node' }

  const depletion = await loadDepletion(tx, serverId, ark.regionId, slot, epoch)
  const remaining = node.totalYield === null
    ? null : node.totalYield - depletion.harvestedUnits

  const position = await loadPosition(tx, serverId, playerId, ark.regionId, slot, epoch)
  const units = accrue({
    lastSettledAt: position.lastSettledAt, now,
    ratePerHour: node.ratePerHour, arrayTier: ark.harvestArrayTier, remaining,
  })

  const grants = baseStockFor(units, ark.harvestArrayTier, node.type)
  if (await rosterCount(tx, serverId, playerId) + grants.length > rosterCap(ark.hatcheryTier))
    return { kind: 'roster_full' }

  await credit(tx, serverId, playerId, 'shards', units, 'node_claim', 'node', `${slot}:${epoch}`)
  const creatures = await grantBaseStock(tx, serverId, playerId, grants)
  await settlePosition(tx, position, now)
  await addHarvested(tx, depletion, units, remaining !== null && units >= remaining ? now : null)

  return { kind: 'ok', shards: units, creatures }
}

/**
 * ONE function. `preview` returns this; `commit` samples it. Two functions
 * would make bible §2.6's published odds a claim about code rather than a
 * property of it, and the convergence test above could not exist.
 */
export function spliceDistribution(a: Creature, b: Creature,
                                   locked: TraitRef, bundle: Bundle): Distribution {
  const pool = combatPool(a, b).filter(t => !isLocked(t, locked))   // the remaining three

  const combat2 = pool.map(t => ({
    trait: t.trait,
    // design §5.3, floored at Tier I per that section's derivation.
    tier: bundle.traitById(t.trait).dominant ? t.tier : Math.max(1, t.tier - 1),
    p: 1 / pool.length,
  }))

  return {
    combat2,
    instinct: [a.instinct, b.instinct].map(i => ({ instinct: i, p: 0.5 })),
    mutation: 0.09,
    aberrant: 0.05,
  }
}

export async function commitSplice(tx: Tx, serverId: number, playerId: string,
                                   req: SpliceRequest, now: Date): Promise<SpliceResult> {
  const [a, b] = await loadOwnedCreatures(tx, serverId, playerId, [req.parentA, req.parentB])
  if (!a || !b)                          return { kind: 'not_owned' }
  if (a.committedTo || b.committedTo)    return { kind: 'creature_committed' }

  const ark = await loadArk(tx, serverId, playerId)
  const generation = Math.max(a.generation, b.generation) + 1
  // Blocked, not truncated. splice_confirm_spec §2: surface the Chamber
  // upgrade rather than a bare error.
  if (generation > maxGeneration(ark.splicingChamberTier))
    return { kind: 'generation_ceiling', ceiling: maxGeneration(ark.splicingChamberTier) }

  // design §5.2: the body is a free choice between the two parents' species -
  // "free" meaning unrandomised, NOT unconstrained. A body that is neither
  // parent's species would let a client mint any species it liked out of two
  // it owns, which is the splice's own version of the ownership hole.
  if (req.bodyFrom !== a.species && req.bodyFrom !== b.species)
    return { kind: 'invalid_body' }

  const seed = randomSeed()
  const outcome = sampleSplice(spliceDistribution(a, b, req.locked, bundle), seed)
