Broodline · System architecture · Sheet 2

Runtime, data and scale

What each piece is written in, what a request actually touches, how the database is laid out, and what growth costs. The honest conclusion of the load estimate: this is not a large system. The scaling risk in Broodline is operational, not computational — which is why the right-hand column is an ops list rather than a capacity chart.
One core, compiled twice
The highest-risk item in the project: the same simulation must produce bit-identical results on an iPhone and in a Linux container.
Broodline.Sim — plain C#, netstandard2.1
A pure library: no engine dependency, no rendering, no allocation in the hot loop. It lives outside the Unity assembly graph as a compiled DLL rather than as source in Assets/ — an assembly definition with no UnityEngine reference is what physically prevents someone reaching for Time.deltaTime inside it.
Unity 6 client — IL2CPP, ARM64, Metal
Links the core for live play. Unity's own systems are banned from the simulation: no physics, no coroutines, no Update() driving game logic. Unity renders the sim's output; it does not participate in it.
sim service — headless .NET, Linux container
Runs the identical core for wave validation, raid auto-resolve and replays. Short, self-contained, CPU-bound calls — precisely the shape Cloud Run is built for.
compiled into the player
compiled into a container
No floating point
Anywhere in the core. Fixed-point long at Q32.32; trigonometry and square roots come from lookup tables, never from Math.
Fixed timestep
30 Hz. Rendering interpolates between two snapshots; the simulation never sees a variable delta and never learns that rendering exists.
Seeded PRNG
xorshift128+, one stream per simulation, seed supplied by the server. Never System.Random, never UnityEngine.Random.
Deterministic iteration
No Dictionary or HashSet traversal — sorted arrays and stable entity IDs only. This is the failure that always ships, because it is invisible on one machine.
No wall-clock reads
Time is tick count. Determinism holds under IL2CPP because the core contains no floating point and no unordered iteration.
The CI gate is the whole mitigation. A nightly job replays a corpus of a few thousand stored replays on both an iOS device-farm build and the server build, diffing outcome hashes; any drift fails the build. The nightly diff compares CoreCLR against a macOS ARM64 IL2CPP build, and a physical device run before each release closes the remaining gap. Without it the two builds diverge silently within a month — and simulation drift is not a load failure, it is a trust failure: every player who watches a replay that doesn't match what they saw stops believing the game is fair.  Alternative considered and rejected: a Rust core with a Swift/C# FFI shim — stronger determinism guarantees, more velocity than this team should spend. C#, and buy the determinism back with discipline and this gate.
What one request touches
REST/JSON over HTTP/2. No Kubernetes at launch: the workload is stateless request/response plus scheduled jobs.
01
Device
Unity's HTTP stack — the path of least resistance, and the reason this is REST and not gRPC. Roughly 40 calls a session, three sessions a day.
02
Cloud Load Balancing
One front door for the whole fleet, TLS terminated at the edge. Shards live behind it; the client never addresses a shard directly.
03
Cloud Armor
WAF and rate limiting. Worth being clear: this is not the anti-cheat. Server authority is the actual defence — jailbreak detection is worth a token effort and no more.
04
game on Cloud Run
Scales per request to hundreds of instances. Nothing is held in memory that has to be reconstructed. Cloud Run costs roughly one platform engineer a year less than GKE.
05 · the failure that arrives with success
PgBouncer
Transaction-pooling mode in front of every instance, with a hard cap on per-instance pool size. Without it, Cloud Run opens a pool per instance and Postgres runs out of connections long before it runs out of CPU.
06
Cloud SQL Postgres
HA with a failover replica and point-in-time recovery. The ledger makes economy state reconstructible even from a bad restore.
Memorystore Redis
Beside the request path, not in it. One instance per shard-group: hot counters, rate limits, presence, chat pub/sub.
Why REST. The client's query shapes are known and fixed, so GraphQL's flexibility buys nothing while costing a caching story, and the request volume doesn't justify gRPC's friction. Intent endpoints, not CRUD — the server owns what a splice means. Reads take deltas via ?since=<cursor>, so a warm client fetches almost nothing. Config is not an API: event definitions, pack contents, trait tables, wave definitions and strings are a versioned JSON bundle on CDN, which keeps live-ops changes off the API path entirely and CDN-cheap at any scale.
Deploys canary by shard — push to one shard, watch for an hour, roll the fleet. The shard model gives this for free and almost nothing else in the design does. SLOs: /v1/sync p99 under 300 ms · wave validation p99 under 500 ms · raid alert delivered within 5 s p95, which is a gameplay requirement rather than an ops one.

Shard — one Postgres schema, one Redis keyspace
500–1,500 DAU · 30 regions · a closed world. A hot shard moves to its own instance without touching anything else, because nothing joins across schemas.
Design so a migration stays mechanical: shard_id leads every partition key · no cross-shard foreign keys · no global sequences · no primary key globally meaningful, so an eventual shard merge is a re-keying exercise rather than a rewrite. Not Spanner at launch — it is the right answer to a global-writes problem this design does not have, at roughly ten times the cost.

Concurrency — narrow, and named
Player-owned state is single-writer by nature, so it takes optimistic concurrency: a version column, compare-and-set, retry once, conflict on the second failure. No locks. Contended state is exactly three things — node extraction totals, alliance treasury, Stake Hold. Extraction is the one that matters, because depletion tracks total extraction across all harvesters rather than wall-clock time: the running total lives in a Redis atomic counter at shard:{id}:node:{id}:extracted, flushed to Postgres every 30 s and on depletion crossing. Harvest is never ticked — it is computed on read from last_settled_at, so fifty thousand sleeping players cost zero background CPU.

What breaks first, in the order it will actually happen
1
Shard provisioning is manual. Fix before launch: one automated operation, three shards warm.
2
Cloud SQL connection exhaustion. PgBouncer in transaction mode, hard per-instance pool cap.
3
A synchronised weekly tick. Every shard rotating deposits, resolving territory and pushing notifications in the same minute is the largest fan-out in the game. Settled: the topology spec wins — tick hour is one of three fixed slots (APAC, EMEA, Americas prime evening), set at shard creation and never changed, and the tick runs as a five-minute announced maintenance window with an hour of visible countdown. That concentrates a third of the fleet in one window, so the engineering fix is per-shard jitter inside the slot, not a wider spread: territory resolves before node rotation on every shard, start times staggered across the five minutes.
4
Redis hot keys on contested nodes. An Apex Vein with fifty harvesters is one counter taking every write. Survivable at this scale; shard the counter by player-hash into sixteen sub-counters if it isn't.
5
Simulation drift. Not a load failure — a trust failure, and the worst on the list. The nightly cross-platform replay diff is the entire mitigation.
Both open conflicts now resolved against broodline_server_topology.md. Tick hour: three fixed slots, not a 24-hour spread, fixed at creation. Shard assignment: storefront region at signup, no transfers — not an invite-code pin. A player who wants to play with a friend elsewhere gets a free unlinked second account, which means the invite code carries no shard semantics and the referral system must be built without one. Population per shard is derived, not chosen: 500–1,500 DAU, from a Rich Deposit lasting two to four days at 1.5–3 concurrent harvesters.

Overlay layer — reachable from any screen, never in a back stack
Trait Codex
Opened from every trait pip in the app, so making it a destination would put it in the back stack of every screen. Built first — it is a dependency of nearly every screen rather than a screen of its own. Without it the counter system is learnable only by losing.
Confirmation dialog
Two levels — standard, and named-entry for Founders. Never suppressible. One shared component; splice destruction is the case it exists for.
Report / Block
One affordance, six surfaces — chat, recipe cards, profiles, alliances, leaderboard rows and names. Captures surrounding context automatically. Gates store submission.
Mail / Notifications
Raid alerts, alliance notices, event announcements, reward grants — and the apology path: a dropped outbox entry, or a raid resolved without an alert, arrives here.
Settings / Account / Support
Required for submission. Carries the published support contact, the block list and the age-gate result. Accessibility preferences are local — they follow the device, not the account.
Nine shared components
Creature card · trait pip · currency header · probability table · region tile · timer chip · confirmation dialog · gate chip · report control. Prefabs with explicit APIs, built before the screens that use them.
