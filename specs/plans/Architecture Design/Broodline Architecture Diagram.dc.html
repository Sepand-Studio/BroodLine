One client, one authoritative server

One long-lived SSE response per foregrounded client, Redis pub/sub behind it. Its own concurrency settings.
sim · internal only, no public ingress
The same C# core the client links, compiled headless. Validates every wave by re-simulation (~20 ms), auto-resolves raids, serves replays. Version-pinned: the one service that cannot roll forward — a replay must play back under the version it was recorded on.
notify
Direct APNs with token auth — no Firebase on an iOS-only platform. Alliance rally fans out to at most 40 device tokens.
world-tick jobs
Cloud Scheduler → Pub/Sub, one job per shard. Tick hour is assigned at shard creation and spread across the wheel — timezone fairness and load-spreading in one decision.

A shard is a closed world
500–1,500 DAU · 30 regions · no cross-shard raids, alliances or leaderboards · capacity is measured in shards · blast radius is one shard, so deploys canary by shard.
SLOs /v1/sync p99 < 300 ms · wave validation p99 < 500 ms · raid alert delivered in 5 s p95, because a 90-second countdown is meaningless if delivery eats twenty of them.  Degradation sim down → waves queue and reward optimistically, reconciled later; stream down → chat polls; notify down → raids auto-resolve and the defender gets the replay plus a mail.

A wave, end to end
The client plays it; the server decides it happened. Rewards are granted optimistically and reconciled — so the interface must be able to show one being withdrawn.
01 · Device
The tap
A Rally records the tick index, never a timestamp. The input log the server re-simulates from must be exactly what the local run consumed.
02 · Device
Ninety seconds at 30 Hz
A stall steps the engine more times rather than skipping. Rendering degrades on the engine's deterministic entity count — so two players watching one replay see the same fidelity.
03 · Device
The replay is the submission
{ sim_version, seed, terrain_id, both rosters, ordered input log } — roughly 2 KB of inputs, not frames.
04 · Device
Into the outbox
Keyed at action time, so a retry after a kill, a crash or three days offline sends the identical key and cannot double-grant. Flushed on foreground and connectivity, with backoff.
05 · Server
Re-simulation
sim replays the log headless and compares the outcome hash. One wave is ~20 ms of CPU, so validate every wave — do not sample. Mismatch: no reward, one telemetry event.
06 · Server
Ledger, then truth
The grant and its append-only ledger row commit in one transaction. The next sync replaces the client's snapshot — it never merges.
POST /v1/wave/submit
Offline, playable. Campaign waves — the engine is local, so the wave simulates and the submission queues. Also the roster, the Codex and lineage: anything that reads cached state.
Offline, unavailable. Splice (the server rolls, and published odds must be demonstrable), harvest claim, raids, alliance actions, the store. Shown as unavailable rather than failing on submit.
